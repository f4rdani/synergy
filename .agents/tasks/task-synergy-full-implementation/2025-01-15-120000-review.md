# Session flow state machine and universal Leader AI connectivity

Synergy gains a complete frontend-to-backend session flow: a 6-screen SPA (welcome, leader selection, planning chat, plan review, worker execution dashboard, completion summary) wired to a new `SessionFlowController` state machine in the backend. The core design decision is the universal adapter pattern for Leader connectivity -- any CLI tool (opencode, aider, claude-cli, codex-cli), GUI app (cursor, kiro), or direct API provider can serve as the Leader through the same `AppAdapter` trait interface, communicating via PTY stdin/stdout or HTTP calls. Workers always use OpenCode with per-worker proxy isolation.

**Watch for:** Mutex held across `.await` in the leader output pump creates a potential deadlock under contention (confirmed). `choose_leader` passes `adapter_id` as the `bin_path` in `LaunchConfig` instead of resolving the actual binary from adapters.toml (confirmed). No filesystem validation in `select_folder` -- the path is stored without checking existence (confirmed). The completion monitor never transitions to `Complete` -- it stops at `Reviewing` with no code path to advance further (confirmed).

## High-level view

The session flow controller is a linear state machine (`Idle -> FolderSelected -> LeaderChosen -> Planning -> PlanApproved -> Executing -> Reviewing -> Complete`) stored in `Arc<Mutex<SessionFlowController>>`. The controller holds the leader's `AppHandle` directly, coupling the flow state to the I/O channel -- this means every read/write to the leader requires locking the entire flow state.

Leader connectivity works through the existing `AppAdapter` trait: `pick_adapter()` maps an adapter ID to the concrete implementation. CLI-based leaders get a PTY spawned via `GenericCliAdapter`, the API-direct path uses `DirectApiAdapter` with HTTP calls, and GUI adapters have placeholder implementations. The frontend calls `send_to_leader` and receives `leader-output` events uniformly regardless of backing adapter type -- this is the key abstraction that enables connecting to any AI tool.

The frontend is a single-file vanilla HTML/CSS/JS SPA with mock mode for browser preview. The executing screen creates xterm.js terminal instances per worker and subscribes to Tauri events for live output. Plan detection happens client-side during streaming, which means partial plans can be shown prematurely.

The approve-to-execute path is where orchestration starts: plan parsing, task insertion into SQLite, worker spawning, tick loop, and a completion monitor. But the lifecycle has a gap -- the monitor advances to `Reviewing` and stops, with no code to detect leader approval and advance to `Complete`.

<summary>Issues (7)</summary>

1. **Mutex held across await in output pump** -- `spawn_leader_output_pump_tauri` holds the `session_flow` mutex lock while calling `read_leader_output().await`. Restructure to acquire, read, release, then emit.
2. **bin_path is adapter_id, not actual binary** -- `choose_leader` passes `adapter_id` (e.g. "claude-cli") as `LaunchConfig.bin_path` instead of resolving the real binary path from adapters.toml (e.g. "claude" for claude-cli, "codex" for codex-cli). CLI adapters will try to spawn a nonexistent binary.
3. **No path validation in select_folder** -- The command stores whatever string the frontend sends without checking the directory exists. Downstream operations (leader spawn, worker cwd) will fail with confusing errors.
4. **Session stuck at Reviewing** -- The completion monitor advances to `Reviewing` and sends the batch report, but nothing reads the leader's reply to call `advance_to_complete()`. The session will remain in `Reviewing` indefinitely.
5. **No dialog plugin permission** -- `capabilities/default.json` lacks `dialog:default` or `dialog:allow-open`. The frontend's folder picker will be denied at runtime (fallback text input still works).
6. **Leader output pump never terminates on error** -- If the leader PTY crashes mid-session, the pump exits but the frontend `typing` indicator is never cleared.
7. **Tick loop and output pump have no cancellation** -- Background tasks spawn infinite loops with no stored `JoinHandle`. Starting a new session creates duplicate loops against the same `AppState`.

## Leader adapter dispatch and binary resolution

`pick_adapter` in `synergy-ui/src/lib.rs` maps adapter IDs to trait objects:

```rust
fn pick_adapter(id: &str) -> Arc<dyn AppAdapter> {
    match id {
        "opencode" => Arc::new(OpenCodeAdapter),
        "cursor" => Arc::new(synergy_adapter::CursorAdapter),
        "kiro" => Arc::new(synergy_adapter::KiroAdapter),
        "api-direct" | "api" => Arc::new(synergy_adapter::DirectApiAdapter::new()),
        other => Arc::new(GenericCliAdapter::new(other, other)),
    }
}
```

Any unmatched adapter ID falls through to `GenericCliAdapter`, so aider, claude-cli, codex-cli all get PTY spawning through the generic path. The problem is in `choose_leader`:

```rust
let launch_config = LaunchConfig {
    bin_path: adapter_id.clone(), // "claude-cli" -- but the real binary is "claude"
    args: Vec::new(),
    cwd: Some(project_dir.clone()),
    proxy_addr: None,
};
```

The `bin` field from adapters.toml (which maps "claude-cli" to binary "claude", "codex-cli" to "codex") is never consulted. `GenericCliAdapter::launch` will try to spawn a process named "claude-cli" which doesn't exist -- the real binary is "claude". The fix: resolve the binary path from the already-parsed adapters list before constructing `LaunchConfig`.

## Mutex contention in the leader output pump

```rust
fn spawn_leader_output_pump_tauri<R: Runtime>(...) {
    tokio::spawn(async move {
        loop {
            interval.tick().await;
            let mut flow = session_flow.lock().await;  // acquired
            if flow.phase == SessionPhase::Complete || flow.leader_handle.is_none() { break; }
            if let Some(output) = flow.read_leader_output().await {  // held across .await
                // emit event
            }
            // dropped at end of iteration
        }
    });
}
```

`read_leader_output` calls `adapter.read_output(handle).await` while the mutex is held. Every other operation needing `session_flow` -- `send_to_leader`, `get_session_flow_state`, the completion monitor -- will block waiting for the lock. The pump runs every 100ms, so the lock is contended nearly continuously.

For the PTY case, `try_read()` is non-blocking and returns quickly, making this tolerable in practice. But for `DirectApiAdapter`, the lock ordering with `send_to_leader` (which also acquires this mutex) creates a real deadlock risk: the pump holds the lock waiting for output while `send_to_leader` needs the lock to send the message that would produce that output.

## Incomplete lifecycle: Reviewing to Complete gap

`spawn_completion_monitor` advances to `Reviewing`, sends the batch report to the leader, emits `session-state-changed` with `"reviewing"`, then breaks out of its loop. No code reads the leader's subsequent response to detect approval via `leader::is_approval()` and call `flow.advance_to_complete()`.

The leader output pump is still running and will receive the leader's reply, but it only emits raw events to the frontend -- it doesn't parse for approval. The frontend listens for `session-state-changed` with `phase: "complete"` to transition screens, but that event is never emitted from the backend.

The mock mode papers over this: the frontend's `checkComplete()` function independently detects all tasks are done and transitions to the complete screen regardless of backend phase. So mock flow works while the real backend flow will stall at `Reviewing`.

## Capabilities gap for dialog plugin

```json
"permissions": [
    "core:default",
    "core:event:default",
    "core:event:allow-emit",
    "core:event:allow-listen",
    "core:window:default",
    "core:window:allow-set-title"
]
```

Without `"dialog:default"` or `"dialog:allow-open"`, Tauri 2.0's capability system will reject the `window.__TAURI__.dialog.open()` IPC call at runtime. The frontend has a fallback (manual path text input), so the app won't crash, but the native folder picker will silently fail.

## Frontend plan detection during streaming

```javascript
function detectPlan() {
  const lastAssistant = assistantMsgs[assistantMsgs.length - 1];
  const lines = lastAssistant.content.split('\n');
  const numbered = lines.map(l => l.match(/^\s*(\d+)[.)]\s+(.+)$/)).filter(Boolean);
  if (numbered.length >= 2) {
    APP.planText = lastAssistant.content;
    APP.planTasks = numbered.map(m => m[2]);
  }
}
```

This runs on every `leader-output` chunk during streaming. The "Review Plan" button appears as soon as 2 numbered lines arrive, even if the leader is still generating more tasks. A user clicking immediately gets a partial plan. The threshold of 2 is also low enough that non-plan responses containing any numbered list ("I see 2 issues: 1. X 2. Y") trigger false detection. The backend's `approve_plan` will re-parse whatever text is submitted, so the impact is UX-level (partial/wrong task list shown) rather than data corruption.

## Background task accumulation

Neither `spawn_tick_loop`, `spawn_output_pump`, `spawn_leader_output_pump_tauri`, nor `spawn_completion_monitor` store their `JoinHandle`. Calling `handleNewSession` resets frontend state but backend tasks keep running. Starting a second session creates duplicate loops. The worker output pump will break when its broadcast channel closes (old orchestrator dropped), but the tick loop has no exit condition and polls indefinitely against a stale orchestrator.
